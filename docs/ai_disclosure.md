# AI disclosure

This project was built with an AI coding assistant (Claude Code; the commits carry a `Co-Authored-By: Claude
Sonnet 5.5` line). The author gave the requirements and direction in a series of prompts; the assistant wrote
the code, tests and documentation, and ran the tests. This page says which parts, which prompts, and what has
been checked by whom. It is written from the repository and the saved prompt history, not from memory.

**What is checked, and by whom, is kept apart on purpose.** Section 3 lists only what the assistant did and can
show evidence for. Section 4 is for the author: the assistant cannot know what the author checked outside the
conversation, so it does not claim anything there.

## 1. What was made with AI

| Area | Made by AI | Notes |
|---|---|---|
| Database schema, models and migrations (`backend/app/models`, `backend/alembic`) | Yes | To the author's table list and constraints |
| File processing: type detection, PDF, OCR, spreadsheets (`file_router`, `pdf_processor`, `ocr_processor`, `spreadsheet_*`, `pipeline`) | Yes | |
| LLM interface, extraction prompt, snippet verification, invoice splitting (`llm_client`, `extraction_service`, `field_verification`, `invoice_segmenter`, `prompts/extraction_v1.txt`) | Yes | The runtime prompt is listed in section 2.2 |
| Validation rules (`validation_service`) | Yes | Rules and tolerances as specified by the author |
| REST API, Celery worker, security (`api`, `workers`, `core`) | Yes | |
| Search: chunking, embeddings, keyword / semantic / hybrid (`search_service`, `embedding_service`) | Yes | The embedder is a hashing demo, not a language model |
| Web interface (`frontend/`) | Yes | |
| Tests (`tests/`, 536 backend tests, 65 frontend tests, 3 browser scripts) | Yes | Including the test data generators |
| Evaluation system (`evaluation/`) and its unit tests | Yes | The report in the repository is output of a real run, not typed text |
| Sample data (`sample_data/`, `evaluation/labeled_dataset/`) | Yes, generated by scripts | Synthetic, not real invoices |
| Documentation (`docs/`, `README.md`) | Yes | |
| Requirements, scope, decisions about what to build | **Author** | The task was given to the author; the prompts below carry their requirements |

Nothing in the repository is copied from another project by the assistant knowingly; it uses open-source
libraries listed in `backend/requirements.txt` and `frontend/package.json`. Licences were not audited.

At run time the product itself can call an LLM (`LLM_PROVIDER=anthropic`) to read invoice text. With
`LLM_PROVIDER=demo` it uses regular expressions and no AI.

### 2.2 The prompt the product sends to the LLM

[`backend/app/prompts/extraction_v1.txt`](../backend/app/prompts/extraction_v1.txt), versioned in the
repository and recorded by name (`extraction_v1`) in every extraction's `raw_llm_output`. In short: extract
only what the text states, give a verbatim source snippet for every value, return null when unsure, treat the
document text as untrusted data, return JSON matching a schema. The wording was written by the assistant from
the author's requirements (prompt 5).

## 3. Checked by the assistant (with how)

| What | How, and the result |
|---|---|
| Backend test suite | Run on 2026-11-25 against PostgreSQL 18 + pgvector and Tesseract 5.5.4: 508 tests, all passed, coverage 97% ([test_results.md](test_results.md)). The LLM is always a mock |
| Real behaviour that mocks cannot show | A real Celery worker killed with `kill -9` mid-document and a closed Redis port, described in [test_results.md](test_results.md) |
| That tests really test | For a list of changes a deliberately broken version of the code made a test fail (see the same file) |
| Evaluation scoring | 28 unit tests with hand-counted examples. Also a run on a deliberately corrupted copy of the ground truth: the report showed exactly the 5 planted differences (wrong value, missed field, invented field, line item, validation) and the counts matched a hand calculation |
| Frontend | 65 unit tests, type check, lint and production build; 3 browser scripts in `tests/e2e/` |
| Evaluation numbers | Come only from a real run (`evaluation/results.json`). That run used the `demo` extractor on 11 synthetic documents |

**Not checked by the assistant:**

- Anything with a real LLM: no API key was available, so no real extraction accuracy has been measured.
- The Docker setup (`docker compose up`): the `docker` command is not installed on the machine where this was written, so `docker compose up` could not be run.
- Bengali OCR; real-world scans and layouts; real invoices of any kind.
- Dependency vulnerabilities (a known advisory for `next@14.2.18` is noted in `security.md`); licences.
- Whether the design is right for the author's business. The assistant followed the prompts.
